README: the rules of this site

Every rule for how the book is organised, scored and displayed, in one place. If a page on this site seems to disagree with a rule here, the page has a bug or this page is out of date. Fix whichever is wrong.

1. The three levels

Everything in the book is a domain, a topic or a sub-topic. No other word is used for these on the site.

LevelWhat it isExample
DomainA field of study. It is never quizzed and has no due date of its own.Computer Science
TopicSits directly under a domain.Data Structures
Sub-topicSits under a topic, or under another sub-topic, at any depth.Stacks & Queues, then Queues under it, then Circular buffer under that

2. Ids and where things sit

  • An id is a path. It is lowercase words joined by hyphens, with parts separated by /. Example: computer-science/data-structures/stacks-and-queues/queues. A domain has 1 part. A topic or sub-topic has 2 to 5 parts.
  • The id decides the parent. A parent is the id with its last part removed. So .../stacks-and-queues/queues is a child of .../stacks-and-queues. If an id does not start with its parent's id, the topic shows up in the wrong place.
  • Each topic or sub-topic is one of three kinds. It can own a whole page, it can be a section with a #anchor on its parent's page, or it can be a grouping with no page at all (every domain is a grouping).
  • A sub-topic's page is its parent's page by default. It gets its own page only when it needs sub-topics of its own. The one exception on record is Big O: its id is under Complexity, but it is taught on the Data Structures page.
  • Renaming an id means rewriting that id in every past event, in the registry and in every link. Statuses and due dates must come out identical afterwards.
  • Dependencies and contrasts. A topic can list other topics it depends on, and topics it should be contrasted with. Both are ids that already exist.

3. Who writes what

FileWhat it holdsWho may write it

nodes.jsonThe list of every domain, topic and sub-topic: id, title, page, dependencies, contrastsThe teacher adds a new entry with no page. The editor sets pages and forward pointers.
{id}.mdThe written explanation for one topic pageOnly the editor
Everything else the site showsStatus, due dates, charts, status lines, coverage logsNobody. It is computed on every build.

Prose has exactly one writer so two writers can never overwrite each other. Events can come from many writers because they are only ever added to the end.

4. Events

  • There are three kinds: taught, read and quiz_answered. Only quiz questions change a status. Teaching and reading never do.
  • The log is append-only. An event is never edited or removed. The single exception is an id rename (section 2), which rewrites the id inside old events and nothing else.
  • Every event has an increasing number, a time in UTC, a date in the learner's local day, an agent and a topic or sub-topic id.
  • A taught event must hold everything taught, in full. The editor writes the page from it and from nothing else.
  • A quiz_answered event holds each question's full text, a summary of the answer, whether it was correct, the id it tests and the feedback. Each question names its own topic or sub-topic, so one quiz can score several. A question that really tests a prerequisite counts as a review of that prerequisite.
  • A quiz also records gaps: real misunderstandings, each with an id like g86-1. A gap that is retested and still wrong gets a new entry. A resolved gap does not.
  • Every question is tagged recall (define, name properties), explain (how it works, why one thing over another) or predict (what happens if, edge cases, judgment calls).

5. Status and review dates

A topic or sub-topic is either solid or needs review. Nothing is ever marked finished, because almost everything has more depth to return to.

  • Streak. Each quiz that names a topic counts as one review. A review with no wrong answer adds 1 to its streak. A review with any wrong answer resets the streak to 1. A review that is mostly right with one real misconception counts as wrong.
  • Due date. The date of the latest review, clean or missed, plus the gap for the current streak. A miss on 22 September makes the topic due again on 25 September.
  • Solid means the latest review was clean and the due date has not passed. Needs review means the latest review had a miss, or the due date has passed.
  • A topic or sub-topic that has never been quizzed has no due date. It reads "never scored on its own".

6. Parents

A topic or sub-topic that has sub-topics under it is a parent. Parents combine their own result with their sub-topics' results.

  • Status. A parent is only as strong as its weakest part. It is solid only if its own result and all its sub-topics are solid.
  • Due date. A parent is due on the soonest of two things: its own latest quiz, and its sub-topics' due dates. Its own quiz always competes. Example: a quiz on Trees with a miss comes due in 3 days. Trees is then due in 3 days and appears on the review schedule in its own right, even when its sub-topics are due later. When the parent and a sub-topic are due on the same day, the parent's own quiz counts.
  • One exception. A parent's own quiz that is older than a sub-topic's latest quiz counts as superseded. Without this, a topic quizzed once long ago would stay overdue forever while its sub-topics were reviewed. In that case the parent takes the soonest date from its sub-topics, and the sub-topic is the one listed.
  • Domains (and groupings with no page, such as Complexity) take their date from the earliest of their topics, and have none until something under them has been quizzed. They are never listed on their own.

7. The skill grid

Beside each row on the home page are three small boxes: recall, explain and predict. Each box shows the right answers out of the last 10 questions asked with that tag, such as 2/4. A box is green only when at least 5 questions have been asked and at least 80% of them (8 out of 10) were right. Until then it stays in the needs-review colour. A box with no questions shows a dash.

8. The home page

The activity strip

One square per day for the last 28 days. A day is shaded by the number of quiz questions answered: 0, 1 to 2, 3 to 5, 6 to 9, or 10 and above. Active days counts days with at least one question. Longest run is the most days in a row with at least one question. Since last is the days since the latest question.

Next up

One card names what to study next. It follows these rules in order and stops at the first that applies:

  1. Any topic or sub-topic past its own due date. The oldest comes first.
  2. Otherwise walk the domains in study-path order, then their topics, then their sub-topics, and take the first one that is not solid.
  3. If that one depends on something that is not solid, take the dependency instead.
  4. If it is a parent, take its first sub-topic that is not solid. A parent's status is a roll-up, so it can only be cleared by clearing its sub-topics.

The study-path order of domains is: Computer Science, Machine Learning, Mathematics, Databases, Software Engineering, Security, Backend, Frontend.

Waiting for the editor

A box lists every page that has events its prose has not absorbed yet, and every topic or sub-topic that has events but no page. It disappears when the editor has caught up.

The spine

  • Each domain is a heading. Each topic under it is a collapsible row with its sub-topics inside. The topic that "Next up" points to opens by itself.
  • Indentation shows the level. A topic's own row is at the left edge and bold. Its sub-topics are indented one step. Their sub-topics are indented one step further, and so on. No level is flat.
  • A topic's own row appears inside its list only when it has quiz history of its own.
  • Counts such as "7 / 16 solid" cover sub-topics only. A topic with no sub-topics counts as itself.
  • Each row shows its status, its due date or "never scored on its own", how many times it has been reviewed, any unmet dependency, and a plain sentence on where it stands. That sentence is the latest unresolved gap, or the last clean check, or what was taught.
  • Topics that are planned but not yet in the registry show as empty placeholders.

9. The review schedule

  • It lists every topic and sub-topic that has a due date that counts (section 6), soonest first. The most overdue are at the top. A divider marks today.
  • A parent is listed when its own quiz sets its date. If its date comes from a sub-topic, that sub-topic is listed instead, so the same debt is never shown twice.
  • Below the table, "Unscheduled" lists every topic and sub-topic that has never been quizzed on its own, most recently scored first. A quiz on a whole topic scores the topic, not the sub-topics under it.
  • The count of overdue items on this page and on the home page's "Next up" card are the same number.

10. Topic pages

  • Each page has a generated header (title, status line, coverage log) and a body that the editor writes.
  • The body explains the topic timelessly. It has no dates, no session history and no event numbers. Anything the learner got wrong goes in a single "Where things stand" paragraph at the end.
  • A common mistake worth warning every reader about is written as a "tempting but wrong" sentence together with the example that shows why it is wrong.
  • The editor never goes beyond what the events contain. If an event looks factually wrong, the editor leaves it out and flags it.
  • Material beyond the current depth becomes one sentence plus a row in the page's "Intermediate & Advanced Topics" table.
  • Each page records the highest event number already written into it. Any later event that touches the page is its backlog, and the status line says "not yet written up".
  • Prose uses a small fixed set of markdown: headings, paragraphs, bold, italic, code, links, lists, fenced diagrams, callouts and tables. Raw HTML is rejected, so prose can never break the layout. The full list is in docs/prose-format.md in the repo.

11. How sessions are run

  • Theory, analogies and judgment scenarios only. Never programming exercises.
  • A new topic starts with one or two diagnostic questions. They are not scored.
  • Quizzes have at least 3 questions. Each open gap is retested first, with a new scenario. No question is repeated word for word.
  • After each answer, the reply says why it is right or wrong, not only whether.
  • Moving on is earned by solid answers, not by the calendar. Anything overdue gets a recall check before new material.

The reasons behind these rules are on the Teaching Style page.

12. Building and publishing

  • Git holds sources only: events, the registry, the prose files, the page templates, the hand-written pages, the stylesheet, the scripts and the docs. Everything generated goes into a build folder that git ignores.
  • One command rebuilds everything: check the events, compute every status, copy the sources, render each topic page from its prose, fill in the generated parts of the home page, the review schedule and each topic page, and write the agent guide. It stops at the first error.
  • Every push to the main branch rebuilds and publishes the site. A daily rebuild at 06:00 India time keeps "overdue" counts and "Next up" current without a push.
  • Agents that cannot write to the repo paste their events into the Log page. They are checked, stored in an inbox folder, and added to the log by the next build. Bad drafts are rejected with a reason.
  • The Action also commits to the main branch, so always pull before working locally.
  • No status on any page is typed by hand. A wrong number means a wrong event or a wrong rule, never a wrong page.
