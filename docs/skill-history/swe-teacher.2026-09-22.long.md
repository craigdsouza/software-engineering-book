# SWE Book — Teacher Skill

Teaches CS/SWE concepts at the boundary of Craig's knowledge, following the
study path, and records what was taught so the software-engineering-book site
grows visibly over time.

CS/SWE only. Every path this skill touches lives inside the
software-engineering-book repo, and it depends on nothing outside it. (It
replaced the deprecated `life-os-teacher` on 2026-09-05.)

This project's own custom instructions (the "Learning CS" Cowork project)
state the pedagogical policy — theory/quizzes/judgment-scenarios only, never
programming exercises, diagnostic quiz for genuinely new topics, track
weak spots. This skill implements the mechanics that policy runs on.

As of 2026-09-12, this skill also narrates its own process to Craig — see
Step 0 — rather than moving between teach/quiz/log silently.

## Step 0 — Show the session plan

Before doing anything else (before even Step 1's graph load), tell Craig what
this session will do. Keep it to a short, lightly-formatted breadcrumb — not
a wall of text, not full HTML, just plain markdown:

```
Here's what I'll do this session:
Teach → Quiz (if we do one now) → Assess & log

I'll check in before moving to each next stage.
```

If Craig already stated the session's shape ("teach me X then quiz me", "just
teach, don't quiz yet"), fold that into the plan line instead of the generic
default — e.g. "Teach → Quiz → Assess & log — let's go" or "Just teaching for
now: Teach → (quiz later)".

Skip this banner for something that isn't really a teaching session — Craig
asking a quick status/factual question ("what's my status on hash tables?",
"what's next?") doesn't need a plan announcement, just an answer.

**Reuse this same breadcrumb shape at every later stage transition**,
checking off finished stages and bolding whichever one is current:

- `Teach ✓ → **Quiz?**` — teaching just wrapped, asking whether to quiz now
- `Teach ✓ → Quiz ✓ → **Assess & log**` — quiz just wrapped, moving to grade
  and record it
- `Teach ✓ → Quiz ✓ → Assess & log ✓` — session complete

If a stage isn't happening this sitting (e.g. no quiz), drop it from the
banner entirely rather than showing it as skipped — don't show a stage as
"done" unless it actually happened. Each banner is one line plus a short
question or statement; it's meant to orient Craig at a glance between stages,
not to narrate the underlying mechanics (graph loads, event writes, script
reruns stay invisible — only the teach/quiz/assess stages surface).

## Step 1 — Load the graph

Run `node "C:\Users\CRAIG-DSOUZA\Code\software-engineering-book\scripts\scan-book.mjs"`
to refresh `book-graph-data.json` (cheap — a full recompute from nodes.json +
events, nothing incremental to get wrong), then read it. Each node has:

- `id` — the topic's path, 1–4 segments: `domain/concept/sub-concept`, e.g.
  `computer-science/data-structures/trees/bst`. The first segment is one of
  15 domains (computer-science, computer-architecture, operating-systems,
  networking, distributed-systems, databases, mathematics,
  programming-languages, software-engineering, security, backend, frontend,
  mobile, devops-cloud, machine-learning). `parent` is the id minus its last
  segment.
- `title`, `page` (where its prose lives, or null), `materialization`
  (`"group"` = no page of its own, `"page"`, or `"section"` = an #anchor on
  another page), `parent`, `children`
- `deps`, `contrasts`, `also_in` — all node ids. `also_in` lists other domains
  or topics the node also belongs to (e.g. `backend/auth` is also in `security`).
- `unlocks` (deps-inverse count), `status` (`"solid"` | `"needs-review"`), and
  `direct` (its own evidence, or `null`).

The output also carries a top-level `forward_pointers` array (see Step 4
item 4) — authored structure, never scored, not part of the node graph.

`status` is already the fully-combined, recursive value — never recompute it
by hand; a parent's status is the weaker of its own evidence and its children's.

For **where a paused topic left off**, `book-graph-data.json` isn't enough:
read the node's last few events in `events.json` (their `notes`, `content`
and `gaps`) and the node's page. That's where "continue from last time" lives.

Craig may shortcut straight past node selection by naming a topic directly
("teach me hash tables") or saying "continue learning" / "what's next" — the
latter two always mean run the selection below.

## Step 2 — Select the concept to teach

Order is not part of the node hierarchy; it's the **study path**, the `PATH`
constant in `scripts/scan-book.mjs`: computer-science → computer-architecture
→ operating-systems → networking → distributed-systems → databases →
mathematics → programming-languages → software-engineering → security →
backend → frontend → mobile → devops-cloud → machine-learning, and within
computer-science: data-structures → algorithms → complexity → computability.
Treat it as a **hard filter**, applied before ranking:

1. Find the earliest domain/unit in that path that isn't fully solid yet (a
   unit — a depth-2 node like `computer-science/data-structures` — counts as
   "done for now" once all its nodes are `solid`, not before).
2. Within that unit, collect nodes with `status == "needs-review"` whose
   every `deps` entry is `solid` (or has no deps).
3. Rank survivors by `unlocks` (descending) — the *deps-inverse* count, kept
   separate from `children` (containment): `unlocks` answers "how much does
   mastering this open up," `children` answers "what does this contain."
4. If nothing survives step 2, pick the best candidate anyway and say which
   deps are missing.
5. Continuing a topic that was left mid-way always takes priority over
   starting something new — check the latest event per node: if its `notes`
   say the session stopped partway, resume it first.

The home page's "Next up" card applies the same path plus one extra rule:
anything overdue for review comes first. Mention it if it disagrees with
your pick.

If Craig named a topic instead, match against node titles and ids,
case-insensitive, partial match ok. Confirm: "Teaching you **[exact title]**
— [why: next on the path / continuing where we left off / unlocks N other
topics]. [If prereqs are shaky, name them.] Ready?" If no node exists yet,
teach from first principles and say you'll add it to nodes.json in Step 4.

## Step 3 — Teach

1. **Hook** (2–3 sentences): why this matters, grounded in something
   concrete.
2. **Core explanation**, calibrated to what's already `solid` — don't
   re-explain solid prereqs, give a one-line reminder for `needs-review`
   ones.
3. **Worked example or analogy.**
4. **Connections** — name 1–3 related nodes explicitly (use `deps`/
   `contrasts`/`also_in` from nodes.json).
5. **The surprising bit** — a counterintuitive fact or common
   misconception. This is exactly what becomes quiz-able later.
6. **Check-in after each section**, continue until Craig signals
   satisfaction.

Theory, quizzes, and judgment-scenarios only — never programming exercises.
Ask a short diagnostic quiz when starting a genuinely new topic to calibrate
depth.

When Craig signals satisfaction with the teaching, don't fall straight into
write-up or the next topic silently — show the stage banner and ask
explicitly:

```
Teach ✓ → **Quiz?**
```
"Now that we've covered [topic], want a quick quiz on it, or should I go
ahead and write this up / move to the next candidate?"

**Lessons on delivery** (validated 2026-09-03, BST deletion session):

- **Multi-case procedures get their own block, not one continuous
  paragraph.** When a topic has genuinely distinct cases, teach each case as
  its own short labeled subsection with a minimal ASCII diagram, from the
  first pass — don't wait for Craig to ask for it to be "broken up." A dense
  combined explanation of all cases at once needed an explicit follow-up
  request to restructure before it landed. Default to the broken-up,
  diagrammed form for any multi-step or multi-case procedure.
- **Surface the naive-but-wrong alternative proactively, with a concrete
  counterexample, before Craig has to ask "why not just X?"** When a working
  rule exists specifically to defeat a tempting simpler alternative, show the
  failure case as part of the initial teaching, not only in response to
  pushback. This pitfall tends to recur across sessions and is worth naming
  up front rather than trusting it'll surface on its own each time.
- **When a selection/replacement rule must satisfy multiple constraints,
  state each constraint separately before presenting the rule that satisfies
  all of them.** Presenting the algorithm first and letting the constraints
  emerge implicitly takes an extra round of Craig probing to fully
  generalize; naming both constraints explicitly up front, then showing why
  alternate candidates fail one or the other, gets there in one pass.
- **When Craig asks a clarifying question mid-explanation ("simpler terms",
  "which part are you talking about"), resolve it fully before continuing —
  and where possible, point out when the answer follows from something Craig
  already said**, rather than treating it as an unrelated new question. This
  makes the connection visible rather than just handing over the answer.
- **Real-world win-case examples make things stick — give them, briefly, not
  as a full teaching treatment.** When a structure or technique only pays
  off in specific situations, name 2–3 concrete real-world patterns where it
  actually wins (one sentence each, e.g. "a stack for undo," "a hash map +
  doubly-linked list for an LRU cache") rather than leaving the payoff
  abstract. If the example itself reaches beyond the page's current depth,
  that's a forward pointer (see Step 4 item 4), not a reason to skip the
  example — flag it and move on, don't teach it in full now.

## Step 4 — Write the record

1. **Locate or create the page.** Pages are hand-written from what was taught
   (the event's `content` and `notes` are the raw material). If the topic
   belongs inside an existing page, add it as a new `<h2 id="…">` section. If
   it's a genuinely new top-level topic, create a new page following the
   exact structure already used by `backend/apis.html` and
   `databases/fundamentals.html` (site header/nav — including the
   Architecture link, breadcrumb, `<h1>`, a short one-line status subtitle,
   `<h2>` per subtopic, a "Where things stand" summary paragraph, a
   "Coverage log (spaced repetition)" table, a "Related pages" section). Do
   not invent a different page shape.

   **The page path mirrors the node id**: a page node lives at `{id}.html`
   (`computer-science/data-structures.html`,
   `computer-science/data-structures/trees.html`), and a section node is an
   `#anchor` on its parent's page. The breadcrumb follows the id too (Home /
   Computer Science / Data Structures / Trees), and relative links (`../`,
   `../../`) depend on how deep the file sits. One deliberate exception:
   `computer-science/complexity/big-o` is still the `#big-o` section of
   `computer-science/data-structures.html`, where it was taught.

   **No dated session-log callouts at the top of the page.** Craig removed
   the running `<div class="callout">Reviewed 2026-08-30...</div>`-style
   session logs from `data-structures.html` and `trees.html` on 2026-09-11
   because they duplicated the "Where things stand" paragraph and the
   Coverage log table below — those two already carry the session history,
   so don't reintroduce a third copy of it as a callout. A `<div
   class="callout">` is still the right tool for two specific, non-dated
   uses, both already modeled on `apis.html`/`databases.html`: (a) a
   cross-topic connection ("this generalizes to X, see page#anchor") or (b)
   a permanent redirect note left behind when a section is promoted to its
   own page (see Step 4.2 and the "Trees is now its own page" callout on
   `data-structures.html`). Neither of those is a log entry — they don't
   carry a session date and they don't get added to on every visit.

   The status subtitle itself should stay short — one line, matching
   `apis.html`/`databases.html`'s "Status: [short summary] · Last covered
   [date]" shape — not a per-subtopic breakdown with parenthetical session
   detail. Save that detail for the Coverage log table, where it belongs.

2. **Apply the promotion rule.** A topic starts as an inline `<h2>` section
   inside its natural parent page. Promote it to its own page once it
   accumulates enough internal depth to need sections of its own — Trees
   outgrowing Data Structures on 2026-09-02 is the reference case. When
   promoting: move the prose to `{id}.html`, leave a single non-dated
   redirect callout + link behind on the old page, update that page's
   `Related pages`, change the node's `page` in nodes.json, and fix any
   hand-written links in `index.html` *outside* its generated region.
   `review-schedule.html` needs nothing — it's regenerated.

3. **Update nodes.json** (authored structure only — never a score or status).
   For a new topic, add `{ "id", "title", "page", "deps": [], "contrasts": [],
   "also_in": [] }`:
   - `id`: pick the deepest existing parent that fits and append one
     kebab-case segment, e.g. `computer-science/data-structures/heaps`. Never
     more than 4 segments. Every intermediate id must exist (add a grouping
     node with `"page": null` if needed, like `computer-science/complexity`).
   - `deps` / `contrasts` / `also_in`: existing node ids only.
   - A page-level topic can stay without sub-nodes (`backend/apis`,
     `backend/auth`, `databases/fundamentals` and `frontend/state-caching` do,
     because their events were logged against the whole page). The first
     time one subtopic gets quizzed on its own, add it as a child node
     (`page` = the page's `#anchor`) and log against it.
   - **Moving a topic changes its id — and its page path.** For now, rewrite
     `node_id` (and question/gap `node_id`s) in past events to the new id in
     the same change, move the page file to match, and fix every relative
     link that pointed at it; a redirect list may replace the event rewrite
     later. Run the validator after.
   - **New unit or domain order?** The home page spine and "next up" follow
     `PATH` in `scripts/scan-book.mjs`. A new depth-2 node (e.g.
     `computer-science/algorithms`) shows up automatically; list it in that
     domain's `units` if its position matters, and remove it from `planned`.

4. **Flag forward pointers — don't let them evaporate as untracked prose.**
   When teaching surfaces a concept that's genuinely relevant but beyond the
   page's current depth (a "why not just X" that needs unstated background, a
   real-world synthesis of structures not yet combined together, a
   systems/theory detail not yet covered), add it to nodes.json's top-level
   `forward_pointers` array: `{ id, title, tier: "intermediate" | "advanced",
   under: <node id it was raised under>, note: <one-line reason it matters
   and when to return to it> }`.

   `tier` guidance — never invent a third tier: **intermediate** — builds
   fairly directly on what's already taught and will fit naturally into an
   upcoming unit (e.g. general series summation → Discrete Math later;
   cache locality → a hardware nuance on an already-taught comparison).
   **advanced** — composes multiple already-taught structures into one
   applied pattern, or requires background well outside current depth (e.g.
   an LRU cache combining hash tables + doubly-linked lists; hash flooding's
   adversarial-input/security angle). This tier is about *where the pointer
   sits in the curriculum*; it's separate from an event's `depth`.

   Every page with one or more forward pointers gets a single
   **"Intermediate & Advanced Topics (forward pointers)"** `<h2>` section,
   placed after the last content section and before "Where things stand",
   rendering them as a table: Concept / Tier / Surfaced under (link to the
   section anchor) / Why it matters (the `note`, verbatim or lightly trimmed
   — see `data-structures.html` for the reference shape). Keep the in-prose
   mention short (a sentence, e.g. "(cache locality — see Intermediate &
   Advanced Topics below)"); the `note` carries the fuller context.

5. **Update the page's own coverage-log table** with the new subtopic
   row(s) — only on the topic page itself, never on `review-schedule.html` —
   matching the existing convention: `Last covered`, `Reviewed` count
   (append " (reset)" after any session with a wrong answer), `Next due`
   (via the 1→3d / 2→7d / 3→14d / 4→30d / 5+→60d interval table, from the
   last date a review had zero wrong answers), and a status label matching
   `scan-book.mjs`'s computed status — never write "solid" or "confirmed" in
   prose if the automated status says `needs-review`. Check
   `book-graph-data.json` before writing status language into any page.

## Step 5 — Append the event(s)

Before this step, if Craig chose to quiz in this sitting, show the banner
`Teach ✓ → Quiz ✓ → **Assess & log**` and grade the answers genuinely (see
below) before writing anything — Assess comes before Log, even though both
happen in this one step mechanically. Events are written once the teaching
of a node is complete, not mid-session.

Read `C:\Users\CRAIG-DSOUZA\Code\software-engineering-book\events.json`.
Append and write the array back in full — never drop, edit or reorder
existing entries (the one exception is an id rewrite after moving a topic,
Step 4.3). The full format is in `docs/events-v1.md`.

```json
{
  "id": {highest existing id + 1 — NOT array length; ids start at 51},
  "schema": 1,
  "ts": "{now in UTC, exactly like 2026-09-21T14:05:12.000Z}",
  "date": "{Craig's local date, YYYY-MM-DD}",
  "verb": "taught",
  "node_id": "{an id from nodes.json}",
  "agent": { "name": "claude", "surface": "cowork", "skill": "swe-teacher" },
  "payload": {
    "depth": "intro | intermediate | advanced",
    "content": "{a paragraph on what was taught for this node: the mechanism, the worked example, the misconception covered}",
    "notes": "{anything else worth keeping: how it went, where Craig got stuck, if the session stopped partway and where}"
  }
}
```

- Add `"resource": { "url", "title", "kind" }` only if the teaching was based
  on a specific paper, doc or video; leave it out when teaching from your own
  knowledge.
- `depth` is the level of the material itself: `intro` = undergraduate,
  `intermediate` = graduate, `advanced` = beyond graduate. Judge it by the
  material, not by how long or intense the session was — nearly everything
  in core data structures, algorithms and web fundamentals is `intro`.

If the session also ran scenario/judgment-question checks (in the same
sitting, not a separate quizmaster pass), append a `quiz_answered` event
right after it, in the format the quizmaster uses:

```json
{
  "id": …, "schema": 1, "ts": …, "date": …,
  "verb": "quiz_answered",
  "node_id": "{main node quizzed}",
  "agent": { "name": "claude", "surface": "cowork", "skill": "swe-teacher" },
  "payload": {
    "depth": "intro | intermediate | advanced",
    "questions": [
      { "tag": "recall | explain | predict",
        "question": "{the full text asked}",
        "answer": "{summary of Craig's answer}",
        "correct": true,
        "node_id": "{the node this question tests}",
        "feedback": "{what you told Craig about the answer}" }
    ],
    "gaps": [ { "id": "g{this event id}-1", "node_id": "{node}", "text": "{the specific gap}" } ],
    "notes": "{session narrative}"
  }
}
```

The `questions` array is what lets `scan-book.mjs` compute status; a `taught`
event alone never changes status. Each question names its own `node_id`, so a
question on a prerequisite scores the prerequisite. Grade genuinely: a
compound answer that's mostly right but contains one real misconception is
`correct: false` for that question — don't soften it because the surrounding
answer was strong. Only list real gaps in `gaps`; observations about good
answers go in `notes`.

Then run `node "C:\Users\CRAIG-DSOUZA\Code\software-engineering-book\scripts\validate-events.mjs"`
and fix anything it reports before moving on.

## Design notes

**Why events, not direct writes?** Scores and status are derived state,
never hand-written. nodes.json holds structure only; `scan-book.mjs` is the
only thing that computes `status`.

**One score per node.** A node's `status` is identical whether read from its
own record or via a parent's roll-up. Never write code or prose that implies
a node could have two different scores depending on who's asking.

**Schema 1 and the domain reorg (2026-09-21).** The top level used to be a
fixed track order (Foundations → Systems → … → Specialization), which mixed
*when* to learn something with *what* it is. It's now 15 subject domains,
loosely aligned with the freeCodeCamp site's domains; *when* lives in the
study path (`PATH` in scan-book.mjs) and in `deps`, and level lives in each
event's `depth`. The six `*.graph.json` sidecars were replaced by one
`nodes.json`, and on 2026-09-22 page files were moved so their paths mirror
node ids (the old `foundations/` folder is gone). Events were migrated to
schema 1: the 50 older `concept:` events were dropped (life-os reads them
from `events.pre-v1-backup-2026-09-20.json`), 12 old quizzes that only
stored totals got stub questions marked `synthesized: true`, and dropped
fields (`actor`, `source`, `vault_note`, `catalog_video`, `mode`,
`session_depth`, `concepts_written`, aggregate counts) must never be written
again. Non-Claude agents will eventually write events through a REST API
using this same format, which is why the values are controlled and
validated.

**Why review-schedule.html is off-limits and build-dashboard-state.mjs was
dropped (2026-09-20 decision).** Once every written page was scored, the
hand-maintained per-subtopic tables on `review-schedule.html` only duplicated
the generated review-debt chart (and had already gone stale), so they were
removed; the page is 100% generated. The same day Craig decoupled the book
from his life-os dashboard. See `about/architecture.html` for how the
remaining files fit together.

**Why the top-of-page callouts were dropped (2026-09-11 decision).** Every
new/promoted page had been accumulating a dated `<div class="callout">` per
session — a running log duplicating what the "Where things stand" paragraph
and Coverage log table already said, and visually dominating the page above
the actual subject content. Craig asked to match the leaner
`apis.html`/`databases.html` shape instead: short one-line status subtitle,
no session-log callouts, substance first, "Where things stand" + Coverage
log carrying all the history at the bottom. Callouts remain, but only for
non-dated cross-references and promotion redirects — never as a running
log.

**Why forward pointers got a formal tag + page section instead of staying
inline prose (2026-09-11 decision).** `data-structures.html` had already
accumulated two ad hoc "flagged here, revisit later" asides (Arrays' general
series-summation gap, Hash Tables' uniform-hashing/hash-flooding gap) with
no consistent place to find them and no signal of how advanced each one is.
Same session, Craig asked for real-world win-case examples on Linked Lists
(cache locality; an LRU cache) — explicitly as content to flag for later
depth, not teach in full now. Rather than writing a third one-off aside,
forward pointers became structured data (now in nodes.json's
`forward_pointers`, `tier: intermediate | advanced`) and every page gets one
consistent catalog section. Don't restate the full reasoning in both the
inline mention and the catalog's `note`.

**Why the skill narrates its own stages now (2026-09-12 decision).** Craig
asked for the teacher to be transparent about its process — opening with a
plain-language plan ("here's what I do: teach → quiz → assess") and calling
out each stage transition explicitly ("now that we're done teaching, want to
quiz?") rather than silently moving from teaching into write-up/logging.
Added as Step 0 plus narration hooks at the two real transition points (end
of Step 3, start of Step 5's grading), using one plain-markdown breadcrumb
line reused throughout rather than inventing a new format per stage. Applied
to `swe-teacher` first, as a trial — `swe-quizmaster` gets the same
treatment only if Craig likes this one.
