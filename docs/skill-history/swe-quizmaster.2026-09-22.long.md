# SWE Book — Quizmaster Skill

Tests Craig's understanding of CS/SWE topics, scores each session, and writes
the result as an event. This is the grading engine for the Learning CS
project's tutoring sessions, working from the same software-engineering-book
graph that `swe-teacher` teaches from.

CS/SWE only. Every path this skill touches lives inside the
software-engineering-book repo, and it depends on nothing outside it. (It
replaced the deprecated `life-os-quizmaster` on 2026-09-05, deliberately
without that skill's four-level gating + lifetime mastery scoring.)

## Step 1 — Load the graph

Run `node "C:\Users\CRAIG-DSOUZA\Code\software-engineering-book\scripts\scan-book.mjs"`
to refresh `book-graph-data.json`, then read it. Each node carries `id` (a
1–4 segment path, `domain/concept/sub-concept`, e.g.
`computer-science/data-structures/trees/bst`), `title`, `page`,
`materialization` (`group` | `page` | `section`), `parent`, `children`,
`deps`, `contrasts`, `also_in` (all node ids), `unlocks`, `status`
(`solid`/`needs-review`), and `direct` (its own evidence or `null`). `status`
is already the fully-combined recursive value — read it as-is, never
recompute by hand.

---

## Step 2 — Select the node to quiz

**If Craig named a topic:** match against node titles and ids,
case-insensitive, partial match ok. Confirm: "Quizzing you on **[exact
title]** — ready?" If no node exists, quiz from first principles and flag
that it doesn't exist yet — offer to hand off to `swe-teacher` to add it to
nodes.json and write the page first (an event can only point at a node that
exists).

**If no topic specified**, in priority order:

1. **Left partway** — the most recent event on a node says (in its `notes`)
   the session stopped before finishing. Resume this first.
2. **Needs-review, overdue** — `status == "needs-review"` because the due
   date (`direct.dueDate`) has passed. The home page's "Next up" card shows
   the oldest one.
3. **Recently taught, never quizzed** — has a `taught` event but `direct` is
   `null`. Strike while it's fresh.
4. **Solid, not yet due** — lower priority, skip unless nothing else
   qualifies.

Within each tier, follow the study path (`PATH` in `scripts/scan-book.mjs`:
computer-science → computer-architecture → operating-systems → networking →
distributed-systems → databases → mathematics → programming-languages →
software-engineering → security → backend → frontend → mobile → devops-cloud
→ machine-learning) unless Craig explicitly asks for something specific.

**Targeting prior gaps (added 2026-09-11).** For any node selected because
it's `needs-review`, read its most recent `quiz_answered` event(s) in
`events.json` before drafting questions and collect the `payload.gaps`
entries whose `node_id` is this node (each has an `id` like `g82-1` and a
`text`). If any exist, Step 3 must explicitly retest each one this session.
A session that only asks new questions and never revisits a documented gap
can leave the status unmoved even though the quiz felt fine — the scoring
formula only rewards a *clean* sweep, and that has to include the concept
that was actually missed.

Announce the pick and why.

## Step 3 — Run the adaptive quiz

No gating ladder — ask whatever mix of Recall/Explain/Predict questions fits
the node and Craig's apparent depth, matching this project's
"quizzes and judgment-scenario" tutoring style (theory only, never
programming exercises). Minimum 3 questions per sitting. Never repeat a
question already asked verbatim in a prior session on this node (past
events now store the full question text, so check) — a fresh scenario
testing the same concept is fine and often better.

**If Step 2 found outstanding gaps, cover those first.** Construct at least
one fresh scenario per logged gap — a new example probing the same
misconception, never a verbatim repeat. Tell Craig up front, e.g. "First,
let's retest the thing you got wrong last time: ..." — don't silently fold
it into generic questions.

**Tag every question as you ask it**, by type:
- **recall** — "define X," "name the key properties," "what problem does X
  solve"
- **explain** — "walk me through how X works," "why choose X over Y"
- **predict** — "what happens if...," edge cases, judgment scenarios asking
  Craig to reason about an unfamiliar situation using the concept. This is
  the tag that matches most of what this project actually asks — lean on
  it.

**Note which node each question tests.** Usually it's the node being
quizzed; if a question really tests a prerequisite (from `deps`) or a
contrasted node, record that node's id on the question — it will count as a
review of that node instead.

Draw questions from the node's `deps`/`contrasts` in nodes.json so they're
concept-specific, not generic definition exercises. After each answer: brief
direct feedback (correct/incorrect + one sentence why), and for wrong
answers, probe to find the specific gap, explain it, and construct a fresh
counterexample or scenario when a misconception needs correcting, rather
than just restating the rule. If Craig pushes back with a valid point that
narrows or breaks the explanation given so far, treat that as a real
correction to work through fully before moving on.

## Step 4 — Score the session

This is computed by `scan-book.mjs` from the event log, not by the
quizmaster itself — the job here is to log good data (Step 5), then re-run
the scanner and report what it computed. The formula, per node:

- A quiz event counts as a review of every node its questions name. A
  review with zero wrong answers for that node is "successful"; any wrong
  answer for that node resets its streak to 1.
- The streak maps to a due date via 1→3 days, 2→7, 3→14, 4→30, 5+→60 (the
  same table shown on `review-schedule.html`).
- `needs-review` if the most recent review had a wrong answer, or the due
  date has passed; otherwise `solid`.
- A node's status is the weaker of its own direct evidence and the worst
  status among its children — recursively. **There is one status per node,
  full stop.**

Present the result:
> "**[title]**: [status]. [If needs-review: what triggered it — a wrong
> answer, or overdue since [date].] [If solid: next due [date].]
>
> [If wrong answers]: The gap: [specific thing], tagged
> [recall/explain/predict]. [If all correct]: Clean session — logged as [N]
> recall / [M] explain / [K] predict."

## Step 5 — Append the quiz event

Read `C:\Users\CRAIG-DSOUZA\Code\software-engineering-book\events.json`.
Append and write the array back in full — never drop, edit or reorder
existing entries. The full format is in `docs/events-v1.md`.

```json
{
  "id": {highest existing id + 1 — NOT array length; ids start at 51},
  "schema": 1,
  "ts": "{now in UTC, exactly like 2026-09-21T14:05:12.000Z}",
  "date": "{Craig's local date, YYYY-MM-DD}",
  "verb": "quiz_answered",
  "node_id": "{the main node quizzed, an id from nodes.json}",
  "agent": { "name": "claude", "surface": "cowork", "skill": "swe-quizmaster" },
  "payload": {
    "depth": "intro | intermediate | advanced",
    "questions": [
      { "tag": "recall | explain | predict",
        "question": "{the full text of the question asked}",
        "answer": "{summary of Craig's answer}",
        "correct": true,
        "node_id": "{the node this question tests}",
        "feedback": "{what you told Craig about the answer}" }
    ],
    "gaps": [
      { "id": "g{this event id}-1", "node_id": "{node}", "text": "{the specific gap, plain English}" }
    ],
    "notes": "{session narrative: how it went, which prior gaps were retested and how}"
  }
}
```

- `depth` is the level of the material quizzed: `intro` = undergraduate,
  `intermediate` = graduate, `advanced` = beyond graduate. Judge the
  material, not the session's intensity.
- Add `"resource": { "url", "title", "kind" }` only if the quiz was on a
  specific paper, doc or video.
- `questions` is the only source of scores — there are no separate
  correct/wrong totals, and fields like `score`, `max_level_reached`,
  `level_breakdown`, `actor`, `source` or `note` must never be written.
- `gaps`: only genuine gaps. Observations about good answers go in `notes`.
- **Retested gaps:** say in `notes` whether each prior gap (by its id, e.g.
  "g82-1 resolved") is now resolved or still standing. A gap that's still
  standing gets a new entry in this event's `gaps` (new id, current wording)
  so the next session's Step 2 still finds it; a resolved one isn't carried.

Then run `node "C:\Users\CRAIG-DSOUZA\Code\software-engineering-book\scripts\validate-events.mjs"`
and fix anything it reports.

## Design notes

**Why events, not direct writes?** Scores/status are always derived, never
hand-written into a page or nodes.json.

**Why this dropped the leveled gating + lifetime mastery formula.** That
system (used by the older `concept:` events, now only in the pre-v1 backup)
exists to distinguish "can Craig reason about this right now" from "has this
been retained under spaced repetition" — a real distinction, but its
25-reps-per-level threshold assumes a much higher quiz volume per concept
than this curriculum's pace produces. The lighter solid/needs-review scheme
is the same spaced-repetition idea (times-reviewed + gap since last correct),
just made computable. If CS/SWE quiz volume ever grows enough that this feels
too coarse, revisit — don't silently reintroduce those fields without
updating this skill and `swe-teacher` together.

**One score per node** — a page's status and its children's statuses are
read from the same recursive computation, never two separate numbers.

**Schema 1 (2026-09-21).** Events moved to a controlled format so other
agents (e.g. Gemini quizzing Craig on a paper) can eventually write them
through a REST API with the same validation. Questions now carry their full
text, their own `node_id` (one quiz can score several nodes), and gaps carry
ids so a later quiz can say which one it resolved. The 12 oldest quiz events
only stored totals, so their questions are stubs marked `synthesized: true`
— never write that flag yourself. Topic ids changed from `book:foundations/…`
to domain paths the same day; see `docs/events-v1.md`.

**Why Step 6 renders pages (2026-09-20).** The skill used to run
`build-dashboard-state.mjs` for the life-os dashboard but never ran
`build-progress.mjs`, so a quiz's result showed up in the data files but not
on the book's own pages until some later teacher session re-rendered them.

**Why gap-targeting got added (2026-09-11 decision).** Before this, node
selection only looked at whole-node status and question drafting only pulled
generically from `deps`/`contrasts` — nothing connected a specific documented
gap (e.g. "deletion given only a forward pointer, no predecessor" on Linked
Lists) back to the next quiz on that node. A session could ask three good new
questions, get them all right, and still leave the original misconception
unverified. Fixed by reading the prior event's `gaps` as part of node
selection and requiring Step 3 to construct a fresh scenario for each one
before moving to new material, with the outcome recorded explicitly so an
unresolved gap never silently drops off the record.
